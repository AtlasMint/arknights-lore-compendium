# v1.1: Local reader

**Theme:** open model → text, on your own machine
**Outcome:** screenshots are read by an open-weight model running locally. No API key, no per-image cost, and the v1 "Done when" checks can finally be run.
**Status:** built 2026-10-01. All tasks are done; the fan check on real screenshots is still open. See [Outcome notes](#outcome-notes).

## Goal

Swap the one piece of v1 that needs a paid service. v1 put the reader behind a one-function contract (`vision/reader.py` calls an engine's `read()` and caches the result by image hash), so this is one new engine module and one deleted one. The review step, the matcher and the graph don't change.

## The model: Qwen3.5-2B

Hugging Face: [Qwen/Qwen3.5-2B](https://huggingface.co/Qwen/Qwen3.5-2B). Apache-2.0. The small series (0.8B–9B) came out on 2026-03-02. Natively multimodal, so one model reads the image and writes the answer with no separate OCR stage. Non-thinking by default, which is what a read-this-text task wants.

The shortlist, looked at on 2026-10-01:

| Model | Params | License | OCRBench | Verdict |
|---|---|---|---|---|
| **Qwen3.5-2B** | 2B | Apache-2.0 | 84.5 | Pick. Best OCR score at this size, non-thinking by default, 2.7 GB through Ollama. |
| Qwen3.5-4B | 4B | Apache-2.0 | 85.0 | Fallback if names are misread. Thinks by default, so `think` must be off. |
| Qwen3-VL-2B-Instruct | 2B | Apache-2.0 | 79.2 | The Oct 2025 model Qwen3.5 replaced; Qwen's own table has Qwen3.5-2B ahead on OCR. |
| PaddleOCR-VL-1.6, GLM-OCR | 0.9B | Apache-2.0 / MIT | – | Document parsers (PDF → markdown). Built for pages, not a game UI, and no prompt for "which line is the speaker". |
| PP-OCRv5, EasyOCR | tiny | Apache-2.0 | – | Classic scene-text OCR: text lines with boxes, no speaker/text structure. Would need layout rules here. This is v2's PaddleOCR comparison. |
| Florence-2, SmolVLM2 | ≤2.2B | MIT / Apache-2.0 | – | Older and weaker at reading text. |
| Gemma 3 4B | 4B | Gemma licence | – | Not an open-source licence. |

OCRBench numbers come from the Qwen3.5-2B model card's comparison table (non-thinking mode where the card lists both). Nothing has been measured on Arknights screenshots yet; that is the "Measure" task below.

## The runtime: Ollama

[Ollama](https://ollama.com) runs the same weights, quantized, as a local HTTP service. Its `qwen3.5:2b` tag is the Hugging Face release with the vision encoder included (2.7 GB download, about 4 GB of RAM while loaded; this Mac has 24 GB). The tags need Ollama 0.17.7 or newer; Homebrew's is 0.35.

Its code shape is the same as `gemini_reader.py`: one `urllib` POST with a base64 image, one JSON reply. Nothing new in `requirements.txt`, and `python-dotenv` leaves with the key.

Why not the other ways to run a Hugging Face model:

- **`transformers` + `torch`:** about 2.5 GB of wheels, a 4–5 GB model inside the Flask process, and MPS is the slowest of the Mac backends. It loads on the first request (10–20 s), twice with the dev reloader.
- **`mlx-vlm`:** fastest on Apple Silicon, but Mac-only, and the project runs on Windows and Linux too. Ollama has `-mlx` tags (`qwen3.5:2b-mlx`, in preview) that get most of this speed; the plain tag uses Metal through llama.cpp. Worth trying if speed is short.
- **`llama-server -hf unsloth/Qwen3.5-2B-GGUF:Q4_K_M`:** the closest to "straight from Hugging Face": one binary that downloads the GGUF and its vision projector from the Hub, with an OpenAI-style API and JSON-schema output. What it costs is a third terminal to start it in and naming a quantization. If Ollama is unwanted, this is the swap, and it is about the same ten lines of code.

## Flow

```
Upload → Flask → Ollama (qwen3.5:2b) → {speaker, text} → term index → chips → v0 graph
```

Only the second arrow changes.

### Reader
- [x] `vision/ollama_reader.py`: `read(image) → {speaker, text}` as one `POST {READER_URL}/api/chat`:

  ```json
  {"model": "qwen3.5:2b", "stream": false, "think": false,
   "messages": [{"role": "user", "content": "<the v1 prompt>", "images": ["<base64>"]}],
   "format": {"type": "object", "properties": {"speaker": {"type": "string"}, "text": {"type": "string"}}, "required": ["speaker", "text"]},
   "options": {"temperature": 0}}
  ```

  The reply's `message.content` is the JSON string. `format` is enforced as a grammar, so the shape is guaranteed; v1's `parse()` stays as the fallback for an empty or odd reply. `temperature: 0`, because reading text should be repeatable. `think: false` does nothing for the 2B and makes the 4B swap a one-value change.
- [x] Drop `mime_type` from the engine contract: Ollama sniffs the bytes, and `app.py`'s upload check already did the validating. `reader.py` passes just the bytes.
- [x] Errors a user can act on: connection refused → "Ollama isn't running: `brew services start ollama`"; HTTP 404 → "Model not pulled: `ollama pull qwen3.5:2b`". v1's 502 wrapping in Flask stays.
- [x] `reader.py` imports `ollama_reader`; `git rm backend/vision/gemini_reader.py`
- [x] Remove `python-dotenv` from `requirements.txt`, `GEMINI_MODEL` from `config.py`, and the `.env` step from the README. The key ends up nowhere.

## Done when

- The three v1 checks, now runnable: a typical story dialog screenshot gives a relevant graph in one flow, the review step fixes any mistakes, and the round trip takes under ~15 s on a cold cache. Expect a few seconds once the model is loaded: a 3B Qwen VL model at 4-bit reads an image and writes 50 tokens in about a second on an M5 Pro (measured June 2026), and this M5 has fewer GPU cores
- `grep -ri gemini` over the repo finds only git history, the v1 notes and this doc
- A fresh clone runs with `pip install`, `brew install ollama`, `ollama pull`, and nothing else

## Out of scope

Fuzzy matching, cropping, keyword ranking, a second engine or an engine switch in `config.py`, and the PaddleOCR comparison: all v2. Fine-tuning. Running the model anywhere but the user's machine.

## Risks

| Risk | Mitigation |
|---|---|
| A 2B model misreads a stylized name | The review step, as in v1. `qwen3.5:4b` is one config change. Fuzzy matching in v2. |
| Big screenshots are slow: the vision encoder's cost grows with pixels, and phone screenshots are 2340×1080 and up | Measure first. If over budget, downscale to about 1280 px wide in the browser with a canvas before upload. No new Python dependency. |
| Ollama unloads the model after 5 idle minutes, so the next read pays the load again | A few seconds for 2.7 GB. Set `keep_alive` in the request if it gets annoying. |
| The `qwen3.5:2b` tag is mutable in Ollama's registry, so a silent update could change results | Once results are measured, pin the digest that `ollama pull` prints, in the README. |
| Ollama isn't running, or the model isn't pulled | The two error messages above, each with the command to run. |
| Windows and Linux users | Ollama runs on both. CI keeps stubbing the reader and never pulls the model. |

## Outcome notes

### Where the build departs from the plan

- **Screenshots are scaled down in the browser.** The risk table had this as the fix if big screenshots were slow, and they were: a 2340×1080 phone shot took 19 s, 1920×1080 took 14 s, 1280×720 took 6 s. `shrink()` in `App.jsx` draws the image onto an `OffscreenCanvas` at 1280 px on the long side (PNG, so no compression artefacts) before upload. At that size the phone shots take 4–5 s and read the same. The reading cache keys on the shrunk bytes, so a re-upload from the same browser is still a cache hit. Anything that isn't an image is sent as is, so the server's 415 still shows.
- **The 2B was not compared with the 4B.** That task was conditional on misread names, and there were none on the synthetic set. It stays the first knob for real screenshots.
- **`gemini_reader.py` was `rm`'d, not `git rm`'d.** v1 was never committed, so Gemini never reached the history. The v1 notes are the record of it.
- **Ollama's Homebrew build pulls `mlx` and `mlx-c` too.** It has the MLX engine, but the plain `qwen3.5:2b` tag runs on the llama.cpp engine; the `-mlx` tags are separate pulls.
- **The error messages name the fix for both platforms:** `brew services start ollama` on macOS, `ollama serve` elsewhere. Both were checked against the real Ollama: a dead port and a model that hadn't finished pulling.

### Measured

M5, 24 GB, Ollama 0.35.0, `qwen3.5:2b`. The screenshots are synthetic, not the game's: a textured background, a dark dialog band, a speaker label and dialog text, at phone 2340×1080, emulator 1920×1080 and 1280×720. Ten shots, six speakers including `Ch'en` and `SilverAsh`, one `???` and one narration line with no speaker.

- Every shot read exactly right, speaker and text, at full size and at 1280 px. Curly apostrophes come back straight. The matcher then found every name: Amiya, Kal'tsit, Reunion, Chernobog, Rhodes Island and Catastrophe from the first line, with Doctor under needs context.
- Reader time with the model loaded: 4.1–5.1 s for the 1280 px phone shots and 5.6–5.8 s at 1280×720, against 19 s and 14 s at full size. A 1280 px phone shot is 787 image tokens; at 2340×1080 it is 2,549.
- Ollama's own breakdown for a 1280 px shot: 2.2 s of prompt evaluation (the image) and 2.0 s to write the 51-token answer. 25 tokens/s of decoding is slow for a 2B model, and may be the JSON grammar or the llama.cpp engine; the MLX tag is the thing to try.
- After Ollama unloads the idle model (5 minutes), the next read takes 7.9 s, 3.6 s of it loading. The very first call after `ollama pull` took 54 s, a one-off warm-up.
- Browser round trip through the real app, from choosing the file to the chips: 4.6 s and 4.5 s for two phone shots. Building the graph from the five SilverAsh chips took 1.5 s. Under 7 s end to end, against the 15 s budget.
- `python -m tests.test_v1` and `test_v0` pass; the frontend lints and builds. CI is unchanged, since the tests still stub the reader.

### Still owed

A typical story dialog screenshot from the game itself has not been through the flow: the synthetic shots have the layout but a clean font and no art behind the text. Real ones decide whether 1280 px and the 2B are enough; `READER_MODEL = "qwen3.5:4b"` in `config.py` and `maxSide` in `shrink()` are the two knobs.
- Speed knobs not tried: `qwen3.5:2b-mlx`, and `keep_alive` in the request to skip the 3.6 s reload after idle.
- The model digest isn't pinned. `ollama list` showed `324d162be6ca` for `qwen3.5:2b` on 2026-10-01; put it in the README if results ever change.
- From v1: gameplay pages that pass the noise filter (`Hope`), names in lower case at the start of a sentence, and titles with commas.
